Okay this is a good start. Now that we have the contextual overview for our UI kit, we'd like to plan for the next stage of development that will attempt to refactor our color system into a better abstraction of color variable names and values. As you'll see in the open files, there is some duplication between button.modules.css and badge.modules.css - we're specifying a specific color variable for our variants and intents. Note that in our system a variant refers to a major component style, and intents refer to primary, secondary, noeffect, success, info, warning, danger etc.

We've read a lot about color design system tokens. 

While keeping the main objectives of our design system as described in our overview context, can you recommend a strategy for refactoring?

We think our tokens should follow a:

element.tone.emphasis.state pattern.

or in our case:

element.intent.emphasis.state pattern.

For example:

element will be - stroke - fill - icon - background 

tone or intent will be - brand (typically maps to theme) - primary - secondary - noeffect - success - info - warning - danger 

emphasis will be - strong - weak - weaker state will be - hover - press - focus - disabled - selected

This is similar to an approach taken by token systems like token studio.

One point to note is that when we combine options in our current system - we're simply adding the variant, intent, and other options to the class list of the component - which produces....

class="button.filled.primary.lg" etc....

... which is not exactly like a BEM-like class attribute system - which would be more like class="button button--filled button--primary button--lg" etc.

Perhaps that's a weakness of our current system. We're not sure - although it's very easy for us to apply our React component props this way, which match the CSS module.css class selectors.

Note that Tokens Studio encourages a separation between primitive (base) tokens and semantic (alias) tokens, with aliases referencing primitives and switching per theme/mode.
